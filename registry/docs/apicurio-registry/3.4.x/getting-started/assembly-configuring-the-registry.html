Configuring your Apicurio Registry deployment

You can configure your Apicurio Registry deployment, including file-based secrets, HTTP caching, HTTP compression, the web console, logging, health checks, observability, and the storage content cache.

For a list of all available configuration options, see Apicurio Registry configuration reference.

Experimental features

An experimental feature is disabled by default and can change incompatibly or be removed in a later release. To use one, enable the feature and set the apicurio.features.experimental.enabled property, which is the experimental features gate, to true. If you enable an experimental feature while the gate is false, Apicurio Registry does not start.

The gate is false by default. It applies to every property whose description in the configuration reference ends with (experimental), for example, apicurio.agents.enabled and apicurio.iceberg.enabled. It also applies to the GitOps and KubernetesOps storage variants, apicurio.storage.kind=gitops and apicurio.storage.kind=kubernetesops.

Apicurio Registry checks the gate at startup, before it initializes storage. When the gate is false, startup fails if you set one of these properties to true or if the storage kind is gitops or kubernetesops. The error names each property that you set, with its description:

The following experimental features are enabled but the experimental features gate ('apicurio.features.experimental.enabled') is not enabled. Either enable the experimental features gate or disable the following properties: apicurio.iceberg.enabled (Enable the Iceberg REST Catalog API)

To start Apicurio Registry, set apicurio.features.experimental.enabled=true or the APICURIO_FEATURES_EXPERIMENTAL_ENABLED=true environment variable, or disable the features that the error names.

Apicurio Registry 3.2 and 3.3 define the gate but do not check it at startup. A deployment that enables an experimental feature without the gate starts on those versions and does not start on 3.4. Before you upgrade such a deployment, set the gate to true or disable the feature.

Loading configuration values from files

You can load a Apicurio Registry configuration value from a file, such as a mounted secret, to keep the value out of the deployment’s environment variables.

Prerequisites

  • You can update and restart the Apicurio Registry deployment.

  • The file contains the required configuration value and is readable by the Apicurio Registry process.

Procedure

  1. Mount the file in the Apicurio Registry container, for example, at /run/secrets/db_password. Use file permissions that restrict access to the processes that need the value.

  2. Set the environment variable for the configuration property with an additional _FILE suffix:

    APICURIO_DATASOURCE_PASSWORD_FILE=/run/secrets/db_password

    Alternatively, configure the property with a .file suffix in the server configuration:

    apicurio.datasource.password.file=/run/secrets/db_password

    The file value takes precedence over a directly configured value for apicurio.datasource.password. Apicurio Registry removes leading and trailing whitespace from the file contents. This mechanism applies to configuration properties resolved by the server, including properties other than passwords.

  3. Restart the deployment to load the value.

    Apicurio Registry caches the value after reading the file. Restart the deployment after changing the file or its configured path.

Verification

  • Check the server log for a message that confirms the file was loaded for apicurio.datasource.password. The message identifies the property without displaying the secret value.

Troubleshooting

  • If the server reports that the file is missing or unreadable, check the mounted path and file permissions. A configured file that cannot be read causes configuration resolution to fail; the server does not fall back to the directly configured value.

Enabling HTTP caching for artifact content

You can enable HTTP cache headers for supported v3 content endpoints so that a reverse proxy can serve repeated requests from its cache.

Prerequisites

  • You can update and restart the Apicurio Registry deployment.

  • A reverse proxy cache is available in front of Apicurio Registry.

  • An artifact version is available for testing content requests.

Procedure

  1. Enable HTTP caching in the server configuration:

    apicurio.http-caching.enabled=true

    The equivalent environment variable is APICURIO_HTTP_CACHING_ENABLED=true.

  2. Set expiration times that match how long your clients can tolerate stale content. For example, the following configuration caches highly cacheable content for one hour and uses shorter periods for content that can change:

    apicurio.http-caching.high-cacheability.max-age-seconds=3600
apicurio.http-caching.moderate-cacheability.max-age-seconds=30
apicurio.http-caching.low-cacheability.max-age-seconds=10

  3. Configure the reverse proxy to use Surrogate-Control, ETag, and Vary response headers.

    The default Vary headers are Accept, Accept-Encoding, and Authorization. Configure the proxy to keep responses for different credentials separate and to enforce your access policy when serving cached responses. Apicurio Registry does not invalidate proxy entries when content access or version state changes.

  4. Restart the Apicurio Registry deployment to apply the configuration.

Verification

  • Request an existing artifact version through the proxy and inspect its response headers:

    curl --include \
  "https://registry.example.com/apis/registry/v3/groups/my-group/artifacts/my-schema/versions/1.0.0/content"

    Replace the URL and artifact coordinates with values from your deployment, and supply authentication if required. For a successful cacheable response, check for ETag, Surrogate-Control, and Vary headers. With the default diagnostic headers enabled, X-Cache-Cacheability identifies the selected cacheability level. Use the proxy’s cache-hit statistics or logs to verify that repeated requests use its cache.

HTTP cache behavior

Apicurio Registry assigns a cacheability level to supported v3 content responses based on the request, version state, and reference handling.

Table 1. HTTP cacheability levels
Level Default expiration Typical behavior

HIGH

864,000 seconds (10 days)

Content identified by an immutable identifier or a specific immutable version can use the longest expiration.

MODERATE

30 seconds

Requests that use version expressions, such as a branch, or retrieve mutable draft content need a shorter expiration.

LOW

10 seconds

Responses whose dependencies can change or whose content identity cannot be determined use the shortest expiration.

NONE

Not applicable

The response does not receive a Surrogate-Control caching policy.
Activation

HTTP caching is disabled by default. Set apicurio.http-caching.enabled=true and keep at least one cacheability expiration greater than zero to activate it. Setting an individual expiration to zero or a negative value suppresses the caching policy for that level.

Scope

Cache headers apply to supported v3 content operations, including content retrieved by global ID and by group, artifact, and version. The server evaluates the request and can reduce its cacheability because of reference handling or version mutability.

Response headers

Surrogate-Control specifies the proxy expiration policy. ETag identifies the response representation, and Vary identifies request headers that distinguish cached representations. These headers do not enable browser caching; the API’s Cache-Control policy remains no-cache, no-store.

Expiration and invalidation

Cached responses can remain available until the proxy refreshes or expires them. Automatic invalidation of reverse proxy entries is not available. Choose shorter expiration times when content changes or access changes must reach clients sooner.

Configuring the Apicurio Registry web console

You can set optional environment variables to configure the Apicurio Registry web console specifically for your deployment environment or to customize its behavior.

Prerequisites

  • You have already installed Apicurio Registry.

Procedure

  1. Set the REGISTRY_API_URL environment variable to override the default REST API URL. For example, https://registry-api.my-domain.com/apis/registry/v3.

    Typically the Apicurio Registry Operator automatically configures the UI component with the REST API v3 URL. Override this value only if your deployment requires a custom URL.

  2. Set the REGISTRY_FEATURE_READ_ONLY environment variable to true to enable read-only mode. The default value is false.

    In read-only mode, you cannot make changes to registered artifacts. For example, the following actions are unavailable:

    • Creating a group

    • Creating an artifact

    • Uploading a new artifact version

    • Updating artifact metadata

    • Deleting an artifact

    REGISTRY_FEATURE_READ_ONLY only hides these actions in the web console. The REST API still accepts them. To refuse every write, enable the storage read-only mode, apicurio.storage.read-only.enabled, as described in Operational guardrails.

Operational guardrails

Apicurio Registry observability with OpenTelemetry

You can configure Apicurio Registry to export telemetry data using OpenTelemetry (OTel) for comprehensive observability. This includes distributed tracing, metrics export by using the OTLP protocol, and log correlation with trace context.

Apicurio Registry is built with OpenTelemetry support and all telemetry signals (traces, metrics, logs) are enabled at build time. However, the OpenTelemetry SDK is disabled by default at runtime. When enabled, Apicurio Registry exports telemetry data to an OpenTelemetry-compatible collector such as Jaeger, Grafana Tempo, or the OpenTelemetry Collector.

The individual signal properties (QUARKUS_OTEL_TRACES_ENABLED, QUARKUS_OTEL_METRICS_ENABLED, QUARKUS_OTEL_LOGS_ENABLED) are build-time properties and cannot be changed at runtime. All signals are already enabled in the Apicurio Registry build. Use QUARKUS_OTEL_SDK_DISABLED=false to enable telemetry at runtime.
Before you configure OpenTelemetry, ensure that you have installed Apicurio Registry and have an OpenTelemetry-compatible backend available, for example, Jaeger, Grafana Tempo, or OpenTelemetry Collector.

To enable OpenTelemetry observability, configure the following environment variables:

Table 3. Environment variables for enabling OpenTelemetry
Environment variable Description

QUARKUS_OTEL_SDK_DISABLED

Set to false to enable the OpenTelemetry SDK and all telemetry signals. Default is true (disabled).

QUARKUS_OTEL_EXPORTER_OTLP_ENDPOINT

The endpoint URL of your OpenTelemetry collector. The port must match the exporter protocol: use http://jaeger:4317 for the default grpc protocol, or http://jaeger:4318 for the http/protobuf protocol.

QUARKUS_OTEL_EXPORTER_OTLP_PROTOCOL

The protocol that the OTLP exporter uses. Default is grpc, which matches collector port 4317. Set to http/protobuf when the endpoint uses HTTP port 4318.
Example: Enabling OpenTelemetry with Jaeger
environment:
  QUARKUS_OTEL_SDK_DISABLED: "false"
  QUARKUS_OTEL_EXPORTER_OTLP_ENDPOINT: "http://jaeger:4317"

When OpenTelemetry is enabled, Apicurio Registry samples 10% of traces by default to reduce processing overhead and control the volume of trace data. To change the sampling ratio, set the QUARKUS_OTEL_TRACES_SAMPLER_ARG environment variable:

Table 4. Environment variables for trace sampling
Environment variable Description

QUARKUS_OTEL_TRACES_SAMPLER

The sampling strategy. This build-time property is set to parentbased_traceidratio in the Apicurio Registry build. You cannot change it at runtime.

QUARKUS_OTEL_TRACES_SAMPLER_ARG

The sampling ratio (0.0 to 1.0). Default is 0.1, which samples 10% of traces.
Example: Production sampling configuration (10% of traces)
environment:
  QUARKUS_OTEL_SDK_DISABLED: "false"
  QUARKUS_OTEL_EXPORTER_OTLP_ENDPOINT: "http://otel-collector:4317"
  QUARKUS_OTEL_TRACES_SAMPLER: "parentbased_traceidratio"
  QUARKUS_OTEL_TRACES_SAMPLER_ARG: "0.1"

If you deploy Apicurio Registry with the Apicurio Registry Operator, you can set the same values in the spec.app.otel section of the ApicurioRegistry3 custom resource instead of environment variables. See OTelSpec.

When you enable the OpenTelemetry SDK and use JSON logging format, Apicurio Registry automatically includes trace context (trace ID and span ID) in log entries. You can then correlate logs and traces.

Example: Enabling structured logging with trace context
environment:
  QUARKUS_OTEL_SDK_DISABLED: "false"
  QUARKUS_LOG_CONSOLE_JSON: "true"

OpenTelemetry features in Apicurio Registry

When OpenTelemetry is enabled, Apicurio Registry provides several observability features that are fully compatible with your existing monitoring setup.

  • Distributed tracing: All REST API requests are automatically traced with spans containing request details, path parameters, and Apicurio-specific attributes such as groupId, artifactId, and version.

  • Storage layer tracing: All storage operations create child spans. You can trace the complete request flow from REST API to database.

  • Kafka tracing: When using KafkaSQL storage, Kafka operations are automatically traced with context propagation.

  • Custom metrics: OpenTelemetry metrics for artifact operations, schema validations, and search requests are exported alongside existing Prometheus metrics.

  • Log correlation: When JSON logging is enabled, trace context is automatically injected into log entries for correlation.

Existing monitoring endpoints continue to function:

  • The Prometheus metrics endpoint is available at /metrics on the management port (default 9000).

  • Health check endpoints (/health/ready, /health/live) are served on the management port (default 9000).

  • All existing Micrometer-based metrics continue to function.

For a running example that traces requests from Kafka producers, consumers and Debezium through Apicurio Registry, and checks the traces in Jaeger, see the OpenTelemetry tracing example.

Changing the Apicurio Registry log level at runtime

You can change the log level of a running Apicurio Registry instance without restarting it by setting the dynamic apicurio.log.level configuration property. The setting applies to the Apicurio Registry loggers in the io.apicurio category.

Prerequisites

  • You have administrator access to the Apicurio Registry instance.

Procedure

  1. Set the log level with the admin configuration REST endpoint. Valid values are TRACE, DEBUG, INFO, WARN, ERROR, OFF, and ALL. The default value is INFO:

    $ curl -X PUT -H "Content-Type: application/json" \
  -d '{"value": "DEBUG"}' \
  http://localhost:8080/apis/registry/v3/admin/config/properties/apicurio.log.level

    Alternatively, use the CLI:

    $ acr server-config set apicurio.log.level DEBUG

    The registry applies the change within a few seconds. The value is stored in the registry storage, so it persists across restarts.

  2. To revert to the original log level, remove the dynamic property. The registry restores the log level that was active at startup:

    $ acr server-config reset apicurio.log.level

HTTP compression in Apicurio Registry

Apicurio Registry 3.3.2 and later gzip-compresses REST API responses for clients that accept gzip, and decompresses gzip-encoded request bodies. Compression reduces the bandwidth that large schemas and search results consume.

Response compression

Apicurio Registry compresses a REST API response only when all of the following conditions are true:

  • The request includes an Accept-Encoding header that accepts gzip. The header accepts gzip when it lists gzip with a quality value greater than 0. If the header does not list gzip, the wildcard * with a quality value greater than 0 also accepts it. The check is case-insensitive.

  • The response does not already carry a Content-Encoding header.

  • The media type of the response is in the quarkus.http.compress-media-types list. The list covers text-based content such as JSON, XML, YAML, GraphQL, and Protobuf schema definitions, but not opaque binary content such as application/zip or application/octet-stream.

  • The dynamic apicurio.rest.compression.enabled property is true, which is the default.

Apicurio Registry does not apply a minimum size threshold. It compresses every response that meets the preceding conditions, including small ones.

When Apicurio Registry compresses a response, it sets the Content-Encoding: gzip header, removes the Content-Length header that described the uncompressed body, and adds Vary: Accept-Encoding so that caches and content delivery networks store the compressed and uncompressed variants separately.

Request decompression

The Quarkus HTTP layer decompresses request bodies that carry the Content-Encoding: gzip header before Apicurio Registry processes them. Request decompression is always on. The apicurio.rest.compression.enabled property does not affect it. The quarkus.http.limits.max-body-size limit of 50 MB applies to the decompressed payload, so Apicurio Registry rejects a small gzip payload that expands beyond the limit with an HTTP 400 or 413 status code.

The TypeScript SDK and the Go SDK gzip-compress request bodies by default. Web browsers send the Accept-Encoding header automatically, and command-line tools such as curl send it when you use the --compressed option.

Apicurio Registry property and Quarkus HTTP settings

Two configuration layers control compression:

  • Apicurio Registry defines the apicurio.rest.compression.enabled property. The property is dynamic, so you can change it at runtime without a restart by using the admin configuration REST API, the CLI, or the Settings tab of the web console. It turns response compression on or off and does not affect request decompression.

  • The quarkus.http.enable-compression, quarkus.http.enable-decompression, and quarkus.http.compress-media-types properties are Quarkus HTTP settings. Quarkus fixes them at build time, so you cannot change the values in the Apicurio Registry image by setting environment variables on a running instance. The Apicurio Registry build sets quarkus.http.enable-compression to false and quarkus.http.enable-decompression to true.

Apicurio Registry serves its REST API through RESTEasy Classic, which writes responses outside the Quarkus HTTP route chain that quarkus.http.enable-compression acts on. For this reason, a writer interceptor in Apicurio Registry performs the response compression, and it reads the quarkus.http.compress-media-types list to decide which media types to compress.

Disabling HTTP response compression at runtime

You can turn gzip compression of REST API responses off and on without restarting Apicurio Registry by changing the dynamic apicurio.rest.compression.enabled property. Disable it when a proxy in front of Apicurio Registry already compresses responses, or when you need to inspect uncompressed responses.

Request decompression stays active regardless of this setting.

Prerequisites

  • You have administrator access to the Apicurio Registry instance.

  • The Apicurio Registry version is 3.3.2 or later.

Procedure

  1. Check the current value of the property:

    $ curl http://localhost:8080/apis/registry/v3/admin/config/properties/apicurio.rest.compression.enabled

    The response is a JSON object with name, value, type, label, and description fields. The default value is "true".

  2. Set the property to false by using the admin configuration REST API:

    $ curl -X PUT -H "Content-Type: application/json" \
  -d '{"value": "false"}' \
  http://localhost:8080/apis/registry/v3/admin/config/properties/apicurio.rest.compression.enabled

    Alternatively, use the CLI:

    $ acr server-config set apicurio.rest.compression.enabled false

    To use the Apicurio Registry web console instead, click the Settings tab, and in the Additional properties section, set the Compression switch to Off.

    Apicurio Registry stores the value in its storage, so the setting persists across restarts. Other replicas apply the change within the configuration refresh interval, which is one minute by default.

  3. To restore the default, reset the property:

    $ acr server-config reset apicurio.rest.compression.enabled

    The equivalent REST API call is DELETE /apis/registry/v3/admin/config/properties/apicurio.rest.compression.enabled.

Verification

  • A request that includes the Accept-Encoding: gzip header returns a response without a Content-Encoding header while the property is false.

Verifying HTTP compression with curl

You can confirm that Apicurio Registry compresses responses and decompresses request bodies by inspecting the HTTP headers that curl sends and receives. Run these checks after you deploy Apicurio Registry behind a new proxy or ingress controller, or when a client reports garbled or oversized responses.

Prerequisites

  • The Apicurio Registry version is 3.3.2 or later, and the instance is reachable, for example at http://localhost:8080.

  • The curl and gzip commands are installed.

  • You have write access to a group in Apicurio Registry to test request decompression.

Procedure

  1. Request a JSON resource with the Accept-Encoding: gzip header and print only the response headers:

    $ curl -sS -o /dev/null -D - -H "Accept-Encoding: gzip" \
  http://localhost:8080/apis/registry/v3/system/info

    A compressed response includes the following headers:

    Content-Encoding: gzip
Vary: Accept-Encoding

  2. Repeat the request without the Accept-Encoding header and confirm that the response has no Content-Encoding header:

    $ curl -sS -o /dev/null -D - http://localhost:8080/apis/registry/v3/system/info

  3. To read a compressed response body on the command line, add the --compressed option, which sends Accept-Encoding and decodes the body:

    $ curl -sS --compressed http://localhost:8080/apis/registry/v3/system/info

  4. Create a gzip-compressed request body that creates an artifact:

    $ cat > create-artifact.json <<'EOF'
{
  "artifactId": "compression-test",
  "artifactType": "JSON",
  "firstVersion": {
    "content": {
      "content": "{\"type\": \"object\"}",
      "contentType": "application/json"
    }
  }
}
EOF
$ gzip create-artifact.json

  5. Send the compressed body with the Content-Encoding: gzip header:

    $ curl -sS -X POST -H "Content-Type: application/json" \
  -H "Content-Encoding: gzip" \
  --data-binary @create-artifact.json.gz \
  http://localhost:8080/apis/registry/v3/groups/default/artifacts

    Apicurio Registry decompresses the body and returns an HTTP 200 response that describes the new artifact.

Verification

  • The first request returns Content-Encoding: gzip and Vary: Accept-Encoding, and the second request returns neither header.

  • The POST request returns a JSON response whose artifact.artifactId value is compression-test.

HTTP compression troubleshooting

The following table lists common symptoms that clients and proxies produce when HTTP compression does not behave as expected, with the cause and the action to take.

Table 10. HTTP compression symptoms, causes, and actions
Symptom Cause Action

The client sends Accept-Encoding: gzip, but the response has no Content-Encoding header.

One of the following:

  • The apicurio.rest.compression.enabled property is false.

  • The response media type is not in the quarkus.http.compress-media-types list, for example the application/zip that the admin export endpoint returns.

  • The header refuses gzip, for example gzip;q=0 or *;q=0.

  • A proxy between the client and Apicurio Registry removed or rewrote the Accept-Encoding header, or decompressed the response before forwarding it.

Check the property value with GET /apis/registry/v3/admin/config/properties/apicurio.rest.compression.enabled. Send the same request directly to the Apicurio Registry service, bypassing the proxy, and compare the headers. Configure the proxy to forward Accept-Encoding unchanged.

curl prints binary characters instead of JSON.

The response is gzip-compressed, and curl does not decode it unless you ask it to.

Add the --compressed option to curl, or pipe the output through gunzip.

A client receives a response that is gzip-compressed twice, or a client library reports a decoding error.

A reverse proxy, ingress controller, or content delivery network in front of Apicurio Registry compresses responses that already carry Content-Encoding: gzip. Apicurio Registry itself never compresses a response that already has a Content-Encoding header.

Configure the proxy to skip responses that already have a Content-Encoding header, or set apicurio.rest.compression.enabled to false and let the proxy compress.

A cache or content delivery network serves a compressed response to a client that did not accept gzip, or the reverse.

The cache ignores the Vary: Accept-Encoding header that Apicurio Registry sets on compressed responses.

Configure the cache to key stored responses on the Accept-Encoding header, or set apicurio.rest.compression.enabled to false.

A gzip-compressed request body fails with an HTTP 400 status code, or Apicurio Registry closes the connection without sending a response.

One of the following:

  • The client sets Content-Encoding: gzip but sends an uncompressed body.

  • A proxy decompressed the body but forwarded the Content-Encoding: gzip header, or removed the header but forwarded the compressed bytes.

  • A version of Apicurio Registry earlier than 3.3.2 received the request. Earlier versions do not decompress request bodies.

Confirm that the Content-Encoding header matches the body encoding at the point where the request reaches Apicurio Registry. For versions of Apicurio Registry earlier than 3.3.2, disable request compression in the client. For example, the TypeScript SDK accepts useDefaultMiddlewares = false as the fourth argument of RegistryClientFactory.createRegistryClient().

A gzip-compressed request body fails with an HTTP 400 or 413 status code although the compressed payload is small.

The decompressed payload exceeds the quarkus.http.limits.max-body-size limit of 50 MB. Apicurio Registry applies the limit to the decompressed size to prevent decompression-bomb attacks.

Reduce the size of the request body.

Setting QUARKUS_HTTP_ENABLE_COMPRESSION, QUARKUS_HTTP_ENABLE_DECOMPRESSION, or QUARKUS_HTTP_COMPRESS_MEDIA_TYPES on a running instance has no effect.

Quarkus fixes these properties at build time, so the values in the Apicurio Registry image cannot change at runtime.

Use the dynamic apicurio.rest.compression.enabled property to control response compression at runtime.

Storage content cache

Apicurio Registry keeps an in-memory, byte-weighted cache of immutable artifact content in front of the storage layer. The cache reduces storage round trips for reads that look up content by content ID or content hash, such as the Confluent-compatible schema lookup by ID that Kafka clients use.

The cache is enabled by default and applies to every storage variant because Apicurio Registry adds it as a storage decorator. The storage content cache is separate from HTTP caching, which sets response headers so that a reverse proxy or CDN can cache REST responses outside Apicurio Registry. The content cache works inside the Apicurio Registry process and also serves requests that HTTP caching does not cover, such as Confluent-compatible requests, which Apicurio Registry returns without cache headers.

Cached reads

A cache entry holds the content bytes, the artifact type, and the parsed references for one piece of content. Apicurio Registry caches only reads whose result depends solely on an immutable content identifier:

  • Content by content ID, for example, GET /apis/registry/v3/ids/contentIds/{contentId} and its /references variant.

  • Content by SHA-256 content hash, for example, GET /apis/registry/v3/ids/contentHashes/{contentHash} and its /references variant.

  • Content and artifact type by content ID, which serves the Confluent-compatible GET /apis/ccompat/v7/schemas/ids/{id} and GET /apis/ccompat/v7/schemas/ids/{id}/schema requests when legacy ID mode is disabled, which is the default.

Apicurio Registry does not cache reads that resolve content through a group, artifact, and version coordinate, or through a global ID, because that mapping can change over time.

Content bytes never change for a given content ID or content hash, so the content-by-ID and content-by-hash entries have no expiry. Apicurio Registry evicts them only when a cache exceeds its size limit. The content-and-type entry also depends on whether an artifact version still references the content, so it has a bounded staleness window.

Apicurio Registry coalesces concurrent misses for the same key into a single storage call. It never caches failed lookups, so a request for content that does not exist always reaches storage.

Bounded staleness window

Apicurio Registry returns 404 Not Found for a content-and-type lookup when the content is orphaned, that is, when no artifact version references it. Orphan status can change after Apicurio Registry caches the entry, most commonly when you delete the last version that references the content. To keep the hot path fast, Apicurio Registry accepts a short window during which a cached content-and-type entry can be stale:

  • Each content-and-type entry expires apicurio.storage.content-cache.hot-path.ttl-seconds after Apicurio Registry writes it. The default is 30 seconds.

  • When you delete a single artifact version, Apicurio Registry resolves the content ID of that version before the delete and invalidates the matching content-and-type entry after the delete. If the lookup fails, the delete still completes and the entry expires through the TTL instead.

  • Other operations that can orphan content, such as deleting a whole artifact or group, importing data, or restoring a snapshot, do not invalidate entries. The TTL bounds the staleness for these cases.

As a result, a Confluent-compatible schema lookup by ID can still succeed for up to the TTL after a bulk operation removes the last referencing version. Set the TTL to 0 to disable the content-and-type cache and remove the window at the cost of a storage query on every lookup.

The scheduled orphaned content cleanup job, configured by apicurio.storage.orphan-cleanup.every, later removes orphaned content rows from storage. Content-by-ID and content-by-hash entries never expire, so a cached copy of removed content remains readable by content ID or content hash until Apicurio Registry evicts it or restarts.

Memory sizing

apicurio.storage.content-cache.max-size sets the maximum weight, in bytes, of each of the three caches separately, not of all caches together. The default is 64 MiB (67108864 bytes) for each cache, so the caches can hold up to about 192 MiB of content in total. The same content can be present in more than one cache, for example, when clients request it by content ID and by content hash.

The configuration reference describes this property as a maximum total weight. The limit applies to each cache separately, so the total memory bound is the configured value multiplied by the number of caches.

Apicurio Registry weighs each entry as the size of the content bytes plus 64 bytes of overhead and 128 bytes for each reference. The weight estimates the payload, not the JVM objects that hold it. When you plan the JVM heap and the container memory limit, count up to three times the configured max-size toward the memory that Apicurio Registry uses under sustained load, in addition to the baseline memory that your capacity planning requires.

To size the cache for your workload, compare the total size of the schemas that clients read most often with the per-cache limit. Use the cache metrics to confirm the result after a change.

Configuring the storage content cache

You can disable the storage content cache, change its size limit, or tune the staleness window for the content-and-type entry. Apicurio Registry reads these settings at startup, so you apply them by restarting Apicurio Registry with updated configuration properties or environment variables.

Prerequisites

  • Apicurio Registry is installed and you can change its configuration properties or environment variables.

  • You can reach the Apicurio Registry management port, 9000 by default, to read metrics.

Procedure

  1. Decide whether to keep the cache enabled. To disable it entirely, set apicurio.storage.content-cache.enabled to false. The default value is true.

  2. Set the per-cache size limit in bytes with apicurio.storage.content-cache.max-size. The default value is 67108864 (64 MiB). For example, set 134217728 to allow 128 MiB in each of the three caches.

  3. Set the staleness window for the content-and-type entry with apicurio.storage.content-cache.hot-path.ttl-seconds. The default value is 30. Set 0 to disable that cache and query storage on every Confluent-compatible schema lookup by ID.

  4. Apply the settings and restart Apicurio Registry. Use configuration properties or the equivalent environment variables:

    Example: Configuration properties
    apicurio.storage.content-cache.enabled=true
apicurio.storage.content-cache.max-size=134217728
apicurio.storage.content-cache.hot-path.ttl-seconds=10
    Example: Environment variables in a container deployment
    environment:
  APICURIO_STORAGE_CONTENT_CACHE_ENABLED: "true"
  APICURIO_STORAGE_CONTENT_CACHE_MAX_SIZE: "134217728"
  APICURIO_STORAGE_CONTENT_CACHE_HOT_PATH_TTL_SECONDS: "10"
Verification

These steps assume the default setting apicurio.ccompat.legacy-id-mode.enabled=false.

  1. Request the same content twice by content ID. Replace 1 with a content ID that exists in your registry:

    $ curl -s http://localhost:8080/apis/registry/v3/ids/contentIds/1 > /dev/null
$ curl -s http://localhost:8080/apis/registry/v3/ids/contentIds/1 > /dev/null

  2. Read the cache metrics from the management port and filter for the content caches:

    $ curl -s http://localhost:9000/metrics | grep 'cache="content'

  3. Confirm the behavior that matches your configuration:

    • When the cache is enabled, cache_gets_total{cache="contentById",result="hit"} increases on the second request and cache_size{cache="contentById"} is at least 1.

    • When the cache is disabled, the output contains no series with a cache="contentById", cache="contentByHash", or cache="contentAndTypeById" tag.

    • When the TTL is 0, the cache="contentAndTypeById" series are absent while the other two caches still report metrics.

  • The hit ratio for a cache is hit / (hit + miss) from cache_gets_total. A high ratio means that most reads avoid a storage round trip.

  • When the hit ratio stays high with few evictions, a smaller limit reclaims memory without affecting throughput.

Configuring Apicurio Registry health checks on OpenShift

Health check endpoints are served on the management interface (port 9000 by default), separate from the main application port (8080). Configure liveness and readiness probes to target port 9000.

You can configure optional environment variables for liveness and readiness probes to monitor the health of the Apicurio Registry server on OpenShift:

  • Liveness probes test if the application can make progress. If the application cannot make progress, OpenShift automatically restarts the failing Pod.

  • Readiness probes test if the application is ready to process requests. If the application is not ready, it can become overwhelmed by requests, and OpenShift stops sending requests for the time that the probe fails. If other Pods are OK, they continue to receive requests.

The default values of the liveness and readiness environment variables are designed for most cases. Change these values only if required by your environment. Any changes to the defaults depend on your hardware, network, and amount of data stored. Keep these values as low as possible to avoid unnecessary processing overhead.
Prerequisites

  • You must have an OpenShift cluster with cluster administrator access.

  • You must have already installed Apicurio Registry on OpenShift.

  • You must have already installed and configured your chosen Apicurio Registry storage in either Strimzi or PostgreSQL.

Procedure

  1. In the OpenShift Container Platform web console, log in using an account with cluster administrator privileges.

  2. Click Installed Operators > Apicurio Registry.

  3. On the ApicurioRegistry tab, click the Operator custom resource for your deployment, for example, example-apicurioregistry.

  4. In the main overview page, find the Deployment Name section and the corresponding DeploymentConfig name for your Apicurio Registry deployment, for example, example-apicurioregistry.

  5. In the left navigation menu, click Workloads > Deployment Configs, and select your DeploymentConfig name.

  6. Click the Environment tab, and enter your environment variables in the Single values env section, for example:

    • NAME: LIVENESS_STATUS_RESET

    • VALUE: 350

  7. Click Save at the bottom.

    Alternatively, you can complete these steps by using the OpenShift oc command. For more details, see the OpenShift CLI documentation.
