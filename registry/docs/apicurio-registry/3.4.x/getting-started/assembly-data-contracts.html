Apicurio Registry data contracts

Apicurio Registry provides a Data Contracts framework that uses the Open Data Contract Standard (ODCS) v3.1 as the native contract format for managing schema contracts between data producers and consumers.

Additional resources

  • Introduction to Apicurio Registry rules

  • Open Data Contract Standard (ODCS)

  • Apicurio Registry REST API documentation

Overview

The Data Contracts framework enables teams to define, enforce, and track formal agreements about schema structure, ownership, and quality using the industry-standard ODCS format.

A data contract in Apicurio Registry combines the following elements:

ODCS format

Contracts are submitted as ODCS v3.1 YAML documents and projected onto schema artifacts.

Metadata

Ownership, classification, SLA, and support information are projected as labels.

Lifecycle

Status tracking (DRAFT, STABLE, DEPRECATED) and promotion stages (DEV, STAGE, PROD).

Quality rules

ODCS accuracy rules are projected as CEL contract rules; completeness and freshness settings are stored as labels.

Field tags

PII and classification annotations, from ODCS contracts or declared in the schema content, are stored as version labels.

Multi-contract support

Multiple contracts can reference the same schema artifact without overwriting each other.

Data contracts are always available. No special configuration is required: submitting a contract is an explicit opt-in action.

ODCS native format

Apicurio Registry uses the Open Data Contract Standard (ODCS) v3.1 as its native contract format. ODCS is a Linux Foundation standard maintained by the Bitol project. When an ODCS contract is submitted, its contents are projected onto the referenced schema artifacts.

Apicurio Registry adopts ODCS for the following reasons:

Industry standard

ODCS is the Linux Foundation standard for data contracts, with ecosystem tooling such as datacontract-cli.

Vendor neutral

Apicurio Registry is the first schema registry to natively support ODCS.

Interoperable

ODCS contracts can be imported, exported, and used with external tools without translation.

Multiple ODCS contracts can reference the same schema artifact. Each contract’s projections are namespaced by contract ID, so they do not interfere:

Contract "orders-contract" → contract.orders-contract.owner.team = orders-team
Contract "billing-contract" → contract.billing-contract.owner.team = billing-team

Updating a contract only affects its own namespaced labels, rules, and tags. Deleting a contract deletes the ODCS_CONTRACT artifact and removes everything the contract projected from every schema artifact any of its versions referenced: its labels, its odcs:{contractId}:* rules, and its field tags.

ODCS projection mapping

When you submit an ODCS contract, Apicurio Registry parses the YAML, stores it as an ODCS_CONTRACT artifact, and projects its contents onto the referenced schema artifacts. Each projection is namespaced by the contract ID.

Table 1. ODCS projection mapping
ODCS section Projected to

info.status

contract.{contractId}.status label (case-insensitive: draft→DRAFT, active→STABLE, deprecated or retired→DEPRECATED, any other value→DRAFT)

info.version

contract.{contractId}.version label

id

contract.{contractId}.id label

info.dataClassification

contract.{contractId}.classification label

team.name / team.domain / team.contact

contract.{contractId}.owner.team, .owner.domain, .support.contact labels

quality.accuracy rules

Artifact-level CEL domain rules named odcs:{contractId}:{name} (kind CONDITION, mode WRITE)

quality.completeness rules

contract.{contractId}.quality.completeness.{field} labels

quality.freshness.maxStaleness

contract.{contractId}.quality.freshness.maxStaleness label

schemas[].fields[].pii / .classification / .tags

field-tag.{contractId}:{fieldPath}|{tagName} labels with value EXTERNAL, set on the version named in location (latest version if omitted)

serviceLevel.availability, serviceLevel.latency.p50, serviceLevel.latency.p99

contract.{contractId}.sla.availability, .sla.latency.p50, .sla.latency.p99 labels (stored, not enforced by registry). Other serviceLevel fields, such as throughput, are not projected.

Other ODCS sections, such as info.title and descriptions, are kept only in the stored contract YAML.

A status from info.status that becomes STABLE or DEPRECATED also sets contract.{contractId}.lifecycle.stable-date or contract.{contractId}.lifecycle.deprecated-date. A field tag whose label key would be longer than 256 characters is skipped, with a warning in the response.

ODCS accuracy rule thresholds (default 1.0) determine the rule’s onFailure action. The rule params contain the source and threshold values.

Table 2. Accuracy rule threshold mapping
Threshold Failure action Behavior

1.0 or higher

ERROR

Rule evaluation stops at this failure.

0.95 to below 1.0

DLQ

The violation is recorded and evaluation continues. No dead letter queue routing is implemented.

Below 0.95

NONE

The violation is recorded and evaluation continues.

ODCS contract example

Submitting a complete ODCS v3.1 contract to Apicurio Registry produces a set of projections on the schema artifacts that the contract references. The example contract and its resulting projections show how each contract section maps to labels and rules on those artifacts.

ODCS v3.1 contract
apiVersion: v3.1.0
kind: DataContract
id: orders-contract
info:
  title: Orders Contract
  version: 1.0.0
  description: Data contract for order events
  status: active
  dataClassification: confidential
team:
  name: orders-team
  domain: commerce
  contact: orders@company.com
schemas:
  - name: OrderEvent
    type: avro
    location: orders/OrderEvent:3
    fields:
      customerEmail:
        description: Customer email address
        pii: true
        tags:
          - PII
          - EMAIL
      totalAmount:
        description: Total order amount in cents
quality:
  accuracy:
    - name: positive-amount
      expression: totalAmount > 0
      threshold: 1.0
    - name: valid-email
      expression: "customerEmail.matches('.*@.*\\\\..*')"
      threshold: 0.99
  completeness:
    - field: orderId
      threshold: 1.0
    - field: customerEmail
      threshold: 0.99
  freshness:
    maxStaleness: PT5M
serviceLevel:
  availability: 0.999
  latency:
    p99: PT1S

When submitted, this contract results in the following projections:

  1. An ODCS_CONTRACT artifact is created to store the YAML.

  2. Namespaced labels are set on the orders/OrderEvent artifact, for example contract.orders-contract.status=STABLE, contract.orders-contract.owner.team=orders-team, and contract.orders-contract.classification=CONFIDENTIAL.

  3. Two CEL contract rules are created: odcs:orders-contract:positive-amount with onFailure=ERROR, and odcs:orders-contract:valid-email with onFailure=DLQ.

  4. Completeness thresholds are stored as labels, such as contract.orders-contract.quality.completeness.orderId=1.0.

  5. Field tags are set on version 3: field-tag.orders-contract:customerEmail|PII=EXTERNAL and field-tag.orders-contract:customerEmail|EMAIL=EXTERNAL.

  6. SLA labels are stored for external monitoring tools.

When you update an ODCS contract with PUT /groups/{g}/contracts/{contractId}, a new contract version is added (re-submitting an existing info.version returns HTTP 409) and the contract is re-projected:

  • The contract.{contractId}.* labels taken from the YAML are replaced. The stage, compatibility group, and lifecycle dates set through the API are kept.

  • The status from info.status is applied only if the contract lifecycle allows moving to it from the current status (see Contract lifecycle). Otherwise the current status is kept, and the response contains a warning.

  • Rules named odcs:{contractId}:* are replaced; a version without quality.accuracy rules removes them. Other rules, such as rules added manually through the contract ruleset API, are preserved.

  • Field tags are replaced on the target version; a version without field metadata removes them.

  • Schemas the previous version referenced and the new version does not lose the contract’s labels, rules, and field tags.

If a projection fails for any reason other than a missing schema artifact, an invalid location, or a missing version, the new contract version is deleted (or the new contract artifact, on a first submission), the contract’s labels, rules, and field tags on every affected schema artifact are put back as they were before the request, and the request fails with HTTP 400. The cause is written to the server log.

Schema location format

The schemas[].location field in an ODCS contract references an artifact in the registry.

groupId/artifactId:version

The following examples show the supported location forms:

orders/OrderEvent:3

Group orders, artifact OrderEvent, version 3.

OrderEvent:latest

Default group, artifact OrderEvent, latest version.

OrderEvent

Default group, artifact OrderEvent, latest version.

Each entry under schemas[] is independent. Projection and field metadata (PII, tags, classifications) apply only to the artifact named in that entry’s location. Cross-artifact schema references inside the Avro/JSON Schema/Protobuf content are not followed during projection. If a nested type lives in another artifact, either add a separate schemas[] entry for that artifact or give it its own contract. For more information, see the artifact references concept in the additional resources.

  • Artifact references and data contracts

Artifact references and data contracts

Schema artifacts can reference other artifacts (for example an Avro OrderEvent that references a shared Address record). Data contracts stay scoped to each artifact. Apicurio Registry does not walk those cross-artifact references when projecting ODCS field metadata.

What happens at evaluation time

When a Kafka record is serialized, nested objects are fully materialized. An Avro GenericRecord contains the nested Address values inline, not a pointer to another registry artifact. The SerDes convert the record to a map by parsing its JSON toString() output:

{
  "orderId": "ORD-123",
  "address": { "street": "123 Main St", "zipCode": "90210" }
}

Each top-level field becomes a CEL variable. CEL expressions that reach into nested records, such as address.zipCode != "", currently fail with an "undeclared reference" error, which counts as a rule failure. Write CEL rules against top-level fields only.

What projection does not do

ODCS schemas[].fields metadata (PII flags, tags, classifications) is projected only for fields that belong to the artifact listed in that schemas[] entry. The projection engine does not resolve artifact references to discover fields that live on another schema.

So you cannot tag address.street as PII from an OrderEvent contract if street is defined on a separate Address artifact. Declare PII on the Address contract (or add Address as its own schemas[] entry) instead.

Why contracts stay per-artifact

  • Ownership stays clear: the team that owns Address declares which of its fields are PII.

  • Changing Address does not force every dependent contract to be re-projected.

  • Conflicting metadata is avoided when two contracts would otherwise both claim the same nested field.

Practical guidance

  • Put field-level PII and tags on the contract (or schemas[] entry) for the artifact that actually defines those fields.

  • Use CEL quality rules on the parent artifact for its top-level fields. Rules on nested values are not supported yet (see above).

  • List every governed schema under schemas[] when one ODCS document should cover several related artifacts.

Upgrade note: Earlier releases projected field tags from every schemas[] entry onto each target artifact. Field-tag projection now uses only the entry whose location resolves to the target artifact. Artifacts with no matching entry receive no projected field tags. Contracts that previously relied on cross-entry tag bleed-through should add a dedicated schemas[] entry per governed artifact.

Field-level tags

Field tags provide semantic annotation of schema fields, enabling you to identify sensitive data and apply tag-based governance.

Field tags are stored as version labels. They come from two sources:

Inline tags

Declared in the schema content (see Supported schema formats). When a version is created through the Core Registry API v3, they are stored as field-tag.{fieldPath}|{tagName} labels with value INLINE. Labels submitted with the version take precedence over extracted tags with the same key. Versions created through the Confluent Schema Registry compatibility API, and draft content updates, do not get inline tags.

External tags

Projected from ODCS contracts as field-tag.{contractId}:{fieldPath}|{tagName} labels with value EXTERNAL, or set manually by using the version labels API.

The following tag names are commonly used:

Table 3. Common field tags
Tag Meaning

PII

Personally Identifiable Information

SENSITIVE

Sensitive data requiring special handling

EMAIL

Email address fields

PHONE

Phone number fields

FINANCIAL

Financial data

HEALTH

Health-related data (PHI)

Supported schema formats

Apicurio Registry extracts inline field tags from the following syntax in schema content.

Avro

tags and confluent:tags field properties. Tags are also read when the schema references named types defined in other artifacts.

{
  "type": "record",
  "name": "User",
  "fields": [{
    "name": "email",
    "type": "string",
    "tags": ["PII", "EMAIL"]
  }]
}
JSON Schema

x-tags and x-confluent-tags extension properties.

{
  "type": "object",
  "properties": {
    "email": {
      "type": "string",
      "x-tags": ["PII", "EMAIL"]
    }
  }
}
Protobuf

The @tag: annotation in documentation comments, and Confluent confluent.field_meta field options.

message User {
  // @tag:PII,EMAIL
  string email = 1;
}

Contract rules

Contract rules define validation and transformation logic associated with artifacts or specific versions. Rules are organized into domain rules (business logic) and migration rules (schema evolution).

When you submit an ODCS contract, its quality.accuracy rules are automatically projected as CEL domain rules on the referenced schema artifact.

Contract rules are evaluated server-side by the rule execution REST endpoint, and client-side by the Java Kafka SerDes. Both merge the global, artifact-level, and version-level rules in the same way (see Global contract rules).

Rules are classified by kind:

CONDITION

Validates a condition and either passes or fails.

TRANSFORM

Modifies data. If the output is a map, it is passed to the next rule.

Rules run in one of the following modes:

WRITE

Executes on serialize (producer side).

READ

Executes on deserialize (consumer side).

WRITEREAD

Executes on both. A rule with no mode also matches any mode.

UPGRADE / DOWNGRADE

Executes during schema migration.

Apicurio Registry supports the following rule types. Rules of any other type are skipped with a warning.

CEL

Common Expression Language for validation conditions and simple transforms, implemented with the cel-standalone library. Supports the full CEL specification, including has(), size(), contains(), startsWith(), parenthesized grouping, and ternary expressions. Each top-level field of the record is a CEL variable: write totalAmount > 0, not record.totalAmount or message.totalAmount. References to fields of nested records fail with an "undeclared reference" error.

JSONATA

JSONata expressions for data transformation. Supports both CONDITION and TRANSFORM (returns transformed data) kinds. Useful for schema migration transforms.

Rules are evaluated as follows:

  1. Disabled rules, and rules whose mode does not match, are skipped.

  2. The remaining rules run in the order in which they are listed in the ruleset.

  3. A CONDITION rule passes only if its result is exactly the boolean true, for both CEL and JSONata. Compilation and evaluation errors count as failures.

  4. When a rule fails, a violation is recorded. The overall result is failed (passed=false) whatever the onFailure action.

The onFailure action controls whether evaluation continues after a failure:

NONE

Evaluation continues with the next rule.

ERROR

Evaluation stops.

DLQ

Evaluation continues with the next rule. No dead letter queue routing is implemented.

How a failed result affects Kafka clients depends on the SerDes fail-on-error setting, not on the onFailure action.

Contract lifecycle

The contract lifecycle tracks the maturity of a schema through defined status transitions.

A contract has one of the following statuses:

DRAFT

The schema is being developed and is not ready for production.

STABLE

The schema is production-ready.

DEPRECATED

The schema is being phased out.

Statuses transition in one direction only:

DRAFT ──────► STABLE ──────► DEPRECATED
   │                              ▲
   └──────────────────────────────┘
         (skip stable)
Reverse transitions are not allowed. The POST /groups/{g}/artifacts/{a}/contract/status endpoint enforces these transitions and sets the lifecycle dates. Any transition from DEPRECATED is rejected with HTTP 409. The contract metadata API (PUT …​/contract/metadata) applies the same rules when it changes the status.

Independently of status, a contract also tracks a promotion stage:

DEV ──────► STAGE ──────► PROD

Promotion is enforced via the POST /groups/{g}/artifacts/{a}/contract/promote endpoint. Promotion is forward-only, starts at DEV, and cannot skip stages (for example, promoting from DEV to PROD fails with "Cannot skip stages. Promote to STAGE first."). Promoting to PROD requires status STABLE. The response is {"stage": "…​"}. The contract metadata API applies the same rules when it changes the stage.

Schema migration

Schema migration allows you to transform data records between different schema versions using migration rules.

Migration rules use the UPGRADE or DOWNGRADE mode and are typically JSONata TRANSFORM rules that reshape data from one version to another. Migration uses only version-level migration rules, set through PUT /groups/{g}/artifacts/{a}/versions/{v}/contract/ruleset. Artifact-level and global migration rules are not used for migration.

Migration rule example (version ruleset)
{
  "domainRules": [],
  "migrationRules": [
    {
      "name": "v1-to-v2-upgrade",
      "kind": "TRANSFORM",
      "type": "JSONATA",
      "mode": "UPGRADE",
      "expr": "$ ~> |$|{'fullName': firstName & ' ' & lastName}|",
      "onFailure": "ERROR",
      "disabled": false
    }
  ]
}

The migration endpoint chains transforms across multiple versions:

curl -X POST \
  http://localhost:8080/apis/registry/v3/groups/my-group/artifacts/my-artifact/contract/migrate \
  -H 'Content-Type: application/json' \
  -d '{
    "fromVersion": "1",
    "toVersion": "3",
    "record": {"firstName": "John", "lastName": "Doe", "amount": 100}
  }'

The service walks the versions between fromVersion and toVersion in artifact version order. For each step it applies the migration rules of the version being moved to: in mode UPGRADE when moving forward, or in mode DOWNGRADE when moving backward. The transforms are chained sequentially.

Response (HTTP 200)
{"passed": true, "transformedRecord": {...}, "violations": [], "executedRules": 1, "failedRules": 0}

Compatibility groups are stored as the artifact label contract.{contractId}.compatibility.group. Compatibility checks do not use them yet.

# Set compatibility group (returns HTTP 204)
curl -X PUT \
  http://localhost:8080/apis/registry/v3/groups/my-group/artifacts/my-artifact/contract/compatibility-group \
  -H 'Content-Type: application/json' \
  -d '{"contractId": "orders-contract", "compatibilityGroup": "v2-family"}'

# Get compatibility group (returns {"compatibilityGroup": "v2-family"})
curl "http://localhost:8080/apis/registry/v3/groups/my-group/artifacts/my-artifact/contract/compatibility-group?contractId=orders-contract"

Kafka SerDes integration

Contract rules can be evaluated during normal Kafka serialization and deserialization using the Apicurio Registry SerDes libraries. No code changes are required beyond configuration.

Enable contract rule evaluation by setting these properties on your Kafka producer or consumer:

Table 4. SerDes contract rule properties
Property Default Description

apicurio.registry.serde.contract-rules.enabled

false

Enable contract rule execution during serialize/deserialize

apicurio.registry.serde.contract-rules.fail-on-error

true

When true, any failed rule throws an exception, whatever its onFailure action. When false, violations are logged as warnings (java.util.logging) and processing continues

apicurio.registry.serde.contract-rules.cache.ttl.seconds

60

How long the fetched ruleset is cached in the client

apicurio.registry.serde.contract-rules.migration.enabled

false

Enable migration in the deserializer

apicurio.registry.serde.contract-rules.migration.target-version

None

Target version for deserializer migration

Contract rule evaluation works as follows:

Rule source

The SerDes fetch the global, artifact-level, and version-level rulesets of the schema version, merge their domain rules by name (the narrowest scope wins), cache them, and evaluate the rules locally in the client. Empty rulesets are cached too. A ruleset that cannot be fetched, for example because the registry is unreachable or refuses the request, is not cached: with fail-on-error=true the record is rejected, and the next record fetches the ruleset again.

Record conversion

Records are converted to maps by parsing the JSON output of their toString() method.

Producer (serializer)

Runs WRITE rules before serialization.

Consumer (deserializer)

Runs READ rules after deserialization.

Results

TRANSFORM output and deserializer migration results are not applied to the record. No dead letter queue routing is implemented; with fail-on-error=false, violations are only logged.

Producer with contract rules example
Properties props = new Properties();
props.put(SerdeConfig.REGISTRY_URL, "http://localhost:8080/apis/registry/v3");
props.put(SerdeConfig.EXPLICIT_ARTIFACT_GROUP_ID, "my-group");
props.put(SerdeConfig.ARTIFACT_RESOLVER_STRATEGY, TopicRecordIdStrategy.class.getName());
props.put(SerdeConfig.CONTRACT_RULES_ENABLED, "true");
props.put(SerdeConfig.CONTRACT_RULES_FAIL_ON_ERROR, "true");
props.put(ProducerConfig.VALUE_SERIALIZER_CLASS_CONFIG, AvroKafkaSerializer.class.getName());
// ... other Kafka producer properties

KafkaProducer<String, GenericRecord> producer = new KafkaProducer<>(props);

Audit log

The contract audit log records every change to the contract state of an artifact.

The audit log records the following operations:

  • CONTRACT_PROJECTED: an ODCS contract version was projected onto the artifact, for example orders-contract 1.0.0

  • CONTRACT_REMOVED: a contract’s projection was removed, because the contract was deleted or its new version no longer references the artifact

  • STATUS_CHANGED: status transitions through the contract status endpoint, for example STABLE → DEPRECATED

  • METADATA_UPDATED: contract metadata updates through PUT …​/contract/metadata

  • PROMOTED: promotions, for example orders-contract: DEV → STAGE

  • COMPATIBILITY_GROUP_SET: compatibility group changes

  • RULESET_CONFIGURED and RULESET_DELETED: changes to the artifact-level ruleset, or to a version-level ruleset (the entry’s version is then set)

Changes to the global contract ruleset do not belong to an artifact and are not in this log. Deleting an artifact, or the group that contains it, deletes its audit entries.

Query the audit log for an artifact (limit defaults to 20, maximum 500):

curl "http://localhost:8080/apis/registry/v3/groups/my-group/artifacts/my-artifact/contract/audit?offset=0&limit=20"
Response
[
  {
    "auditId": 2,
    "groupId": "my-group",
    "artifactId": "my-artifact",
    "version": null,
    "action": "STATUS_CHANGED",
    "principal": "admin",
    "details": "STABLE -> DEPRECATED",
    "createdOn": "2026-05-19T10:30:00Z"
  }
]

Global contract rules

Global contract rulesets provide a baseline set of rules for all artifacts. Artifact-level and version-level rules override global rules by name. Global rules are applied by the rule execution endpoint and by the Kafka SerDes. Reading the global ruleset requires read access; setting or deleting it requires the admin role.

You can also manage the global contract ruleset in the Apicurio Registry web console. Click the Contract rules tab in the console navigation to add, delete, or clear global contract rules without calling the REST API directly.

When rules are executed through the rule execution endpoint, domain rules are merged from three scopes:

  1. Global rules apply to all artifacts and are set through /admin/contracts/ruleset.

  2. Artifact rules apply to a specific artifact and are set through /groups/{g}/artifacts/{a}/contract/ruleset.

  3. Version rules apply to a specific version and are set through …​/versions/{v}/contract/ruleset.

If a rule with the same name exists at multiple levels, the most specific scope wins.

# Set global ruleset
curl -X PUT \
  http://localhost:8080/apis/registry/v3/admin/contracts/ruleset \
  -H 'Content-Type: application/json' \
  -d '{
    "domainRules": [{
      "name": "require-non-empty",
      "kind": "CONDITION",
      "type": "CEL",
      "mode": "WRITE",
      "expr": "size(orderId) > 0",
      "onFailure": "ERROR",
      "disabled": false
    }],
    "migrationRules": []
  }'

# Get global ruleset
curl http://localhost:8080/apis/registry/v3/admin/contracts/ruleset

# Delete global ruleset
curl -X DELETE http://localhost:8080/apis/registry/v3/admin/contracts/ruleset

Method Endpoint Description

REST API examples

Common curl examples for the Data Contracts REST API, including submitting, listing, exporting, and promoting contracts.

Submitting an ODCS contract
curl -X POST \
  http://localhost:8080/apis/registry/v3/groups/my-group/contracts \
  -H 'Content-Type: application/x-yaml' \
  --data-binary @my-contract.yaml
Response
{
  "contractId": "orders-contract",
  "version": "1.0.0",
  "projection": {
    "rulesApplied": 2,
    "labelsApplied": 12,
    "tagsApplied": 3,
    "warnings": []
  }
}
Listing contracts
curl "http://localhost:8080/apis/registry/v3/groups/my-group/contracts?limit=10&offset=0"
Exporting as ODCS
curl http://localhost:8080/apis/registry/v3/groups/my-group/artifacts/my-artifact/contract/export

Rebuilds ODCS v3.1 YAML from the artifact’s projected contract labels, rules, and field tags. Field tags are read from the latest version only, and location is set to group/artifact:latestVersion. Sections that are not projected, such as the title and descriptions, are missing from the export. Returns 404 if the artifact has no contract.{contractId}.id label.

Promoting a contract
curl -X POST \
  http://localhost:8080/apis/registry/v3/groups/my-group/artifacts/my-artifact/contract/promote \
  -H 'Content-Type: application/json' \
  -d '{"contractId": "orders-contract", "targetStage": "STAGE"}'
Getting quality score
curl "http://localhost:8080/apis/registry/v3/groups/my-group/artifacts/my-artifact/contract/quality?contractId=orders-contract"
Response
{"overall": 0.85, "completeness": 0.83, "compliance": 1.0, "stability": 0.67}

The score is informational only. It is weighted as follows:

  • Completeness (30%): artifact description, owner team, support contact, classification, SLA availability, and owner domain are set.

  • Compliance (40%): the artifact has domain rules, and a status is set.

  • Stability (30%): status is STABLE, the artifact has more than one version, and the contract ID label is set.

Executing contract rules
curl -X POST \
  http://localhost:8080/apis/registry/v3/groups/my-group/artifacts/my-artifact/versions/1/contract/execute \
  -H 'Content-Type: application/json' \
  -d '{"mode": "WRITE", "record": {"totalAmount": 100, "status": "active"}}'
Response (HTTP 200, also when rules fail)
{"passed": true, "violations": [], "executedRules": 2, "failedRules": 0}

The endpoint merges global, artifact, and version domain rules by name (the narrowest scope wins). transformedRecord is included only if a rule changed the record. Each violation has ruleName, message, and action fields.

Setting contract metadata directly
curl -X PUT \
  http://localhost:8080/apis/registry/v3/groups/my-group/artifacts/my-artifact/contract/metadata \
  -H 'Content-Type: application/json' \
  -d '{
    "status": "DRAFT",
    "ownerTeam": "Platform Team",
    "ownerDomain": "payments",
    "supportContact": "platform@example.com",
    "classification": "CONFIDENTIAL",
    "stage": "DEV"
  }'
This call replaces the descriptive fields: ownerTeam, ownerDomain, supportContact, classification, and compatibilityGroup. A descriptive field you omit is removed. status and stage change only when given; omitting them keeps them. Other contract labels, such as the projected id, version, sla., and quality., are kept. A status or stage change that the lifecycle does not allow is rejected (HTTP 409 for the status, HTTP 400 for the stage).
Transitioning contract status
curl -X POST \
  http://localhost:8080/apis/registry/v3/groups/my-group/artifacts/my-artifact/contract/status \
  -H 'Content-Type: application/json' \
  -d '{ "status": "STABLE" }'

Configuration

Data contracts are always available; no special configuration is required. Submitting a contract is an explicit opt-in action that does not affect existing registry functionality.

Contract rule enforcement in Kafka client applications is controlled by the SerDes properties described in the Kafka SerDes integration reference.

Data contracts work across all storage variants:

SQL (PostgreSQL, MySQL, MSSQL, H2)

Full support with immediate consistency. The contract_rules table (database upgrade 103) and the contract_audit_log table (database upgrade 106) are created automatically. The global contract ruleset is also stored in contract_rules.

KafkaSQL

Full support. Label writes go through the Kafka journal for multi-node consistency.

GitOps / KubernetesOps

Read-only. Contracts cannot be submitted, and other write operations are rejected.
