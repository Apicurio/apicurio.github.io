Upgrading to Apicurio Registry 3.4

Apicurio Registry 3.4 upgrades in place from 3.3.x and earlier 3.x versions. Most deployments need no changes, but some changes in this version can affect your data, configuration, clients, or extensions. Review this page before you upgrade, together with the release notes.

For the general upgrade procedure, backups, and rollbacks, see the versioning and support policy in Additional resources.

Additional resources

  • Versioning and support policy

Database upgrades in Apicurio Registry 3.4

With SQL storage, Apicurio Registry 3.4 upgrades the database schema to version 115 when it starts. Apicurio Registry 3.3 uses version 109. The upgrade runs automatically, but three of its steps can need your attention.

Duplicate version order values stop the upgrade (schema version 113)

The upgrade adds a unique constraint on the order of versions within each artifact, UQ_versions_3 on (groupId, artifactId, versionOrder). A registry that received concurrent requests to create the first version of the same artifact can hold two versions with the same order. If any exist, the upgrade fails, and Apicurio Registry does not start. The error message lists each affected version:

Cannot add the UQ_versions_3 constraint: 2 versions share a versionOrder with another version of the same artifact. Give each of them a distinct versionOrder or delete the extra ones, then restart.
  groupId=..., artifactId=..., version=..., versionOrder=...

Apicurio Registry does not change these rows itself, because renumbering a version changes the version numbers that Confluent-compatible clients see, and deleting one loses data.

To find out before you upgrade, run this query against the database:

SELECT groupId, artifactId, versionOrder, COUNT(*)
FROM versions
GROUP BY groupId, artifactId, versionOrder
HAVING COUNT(*) > 1;

If it returns rows, give each listed version a distinct versionOrder, or delete the versions that you don’t need, before you upgrade. If the upgrade has already failed, restore the database from the backup that you took before the upgrade, fix the rows, and upgrade again.

Structured content index backfill (schema version 110)

The upgrade indexes the structure of the latest version of every artifact whose type has structured content extraction, which includes Avro, Protobuf, JSON Schema, OpenAPI, AsyncAPI, GraphQL, WSDL, XSD, XML, Iceberg tables and views, Thrift, and the agent card, MCP tool, MCP server, model schema, and prompt template types, so that search filters on structure work with SQL storage. On a registry with many such artifacts, this makes the first startup of 3.4 take longer. Apicurio Registry logs its progress during the backfill.

The other two steps add a table for peer registries (version 111), and remove versions that are no longer drafts from the drafts branch (version 112).

On MySQL, version 114 also widens names, labels, and principals from ASCII to UTF-8 (utf8mb4), so non-ASCII values are accepted. Principal comparisons stay case-insensitive but now tell accented letters apart, so jose no longer matches the role mappings or artifacts of josé.

Native ID sequences replace the row-locked sequences table (schema version 115)

The upgrade replaces the row-locked sequences table, which allocated global IDs, content IDs, and comment IDs, with native database sequences on PostgreSQL and SQL Server, and with AUTO_INCREMENT ticket tables on MySQL. H2 and KafkaSQL storage are not affected. This step has real upgrade impact, covered in full in Upgrading SQL storage to native ID sequences:

  • Rolling upgrades: the schema upgrade deliberately drops the sequences table, so replicas still running a release earlier than schema version 115 fail every write request as soon as any upgraded replica has migrated the schema. Read requests are unaffected. Complete a rolling rollout promptly, rather than leaving mixed-version replicas running.

  • SQL Server 2017 or later is required, because Apicurio Registry reads sys.sequences.last_used_value.

  • New database privileges if Apicurio Registry connects at runtime with a less privileged user than the one that runs the schema upgrade: PostgreSQL needs USAGE, SELECT, and UPDATE on the three ID sequences; SQL Server needs UPDATE on them; MySQL needs INSERT, DELETE, and SELECT on the ID ticket tables.

  • globalId ordering: a globalId value stays unique, but under concurrent writes it no longer strictly follows commit order, and a rolled-back write leaves a gap. Use the version order, not globalId comparisons, to determine the newest version of an artifact.

Changes to JSON Schema compatibility checking in Apicurio Registry 3.4

Earlier versions of Apicurio Registry checked JSON Schema compatibility with a different checker, based on the everit library. If you used JSON Schema compatibility rules before version 3.4, note the following differences:

  • Artifacts in drafts 2019-09 and 2020-12 are now checked. The earlier checker could not load them, and the check failed with an error instead.

  • Rule violations are worded differently, and their context points at the keyword that changed. Update anything that matches the previous text or contexts, for example:

    Change Before 3.4 From 3.4

    Change the type of property a

    Subschema type changed at /properties/a

    The declared 'type' of the schema was changed. at /properties/a/type

    Add a property to required

    Object type property schemas narrowed at /propertySchemasAdded

    A property was made 'required'. at /required/0

    Remove a value from enum

    Combined type subschema not compatible at /

    A value was removed from the 'enum' allowed set. at /enum

  • A new oneOf subschema that can match the same values as an existing one is now reported as incompatible. The earlier checker compared oneOf like anyOf, and accepted such a change.

  • Adding a type inside then or else that an enclosing schema already requires is reported as incompatible, where the earlier checker accepted it. See Known over-strict verdicts in What the JSON Schema compatibility check reports.

  • The apicurio.compat.json-schema.use-apitomy configuration property, which selected the new checker in version 3.3, no longer has any effect, and is deprecated since version 3.4. Setting it to false does not restore the earlier checker. If it is set, Apicurio Registry logs a warning at startup. The property is scheduled for removal in version 4.0. After the removal, Apicurio Registry does not start if the property is still set. Remove it before you upgrade.

Changes to JSON Schema validity checking in Apicurio Registry 3.4

At the FULL level, the VALIDITY rule now validates JSON Schema content with one validator for every draft (4, 6, 7, 2019-09, and 2020-12). The rule applies only to content that you add after the upgrade. Apicurio Registry does not validate stored artifacts again.

  • Valid schemas in draft 2019-09 now pass. Before 3.4, every 2019-09 schema was rejected.

  • Violations are worded differently, and their context is a JSON Pointer to the keyword, for example boolean found, number expected at /items/properties/price/exclusiveMinimum instead of expected type: Number, found: Boolean at #/items/properties/price/exclusiveMinimum.

  • Several problems can be reported at once, at most one for each location.

  • Some content that the specification does not allow, and that was accepted before, is now rejected.

  • A $schema of http://json-schema.org/schema, the alias without a version, is read as draft 7 instead of draft 4, as the compatibility check reads it.

Configuration changes in Apicurio Registry 3.4

The following configuration properties are deprecated in Apicurio Registry 3.4 and will be removed in 4.0. If one of them is set, Apicurio Registry logs a warning at startup. Remove them from your configuration.

Property Why

apicurio.compat.json-schema.use-apitomy

It has no effect. JSON Schema compatibility is always checked with the new checker.

apicurio.usage.dead-threshold-days

It has no effect. A schema version whose last fetch is older than apicurio.usage.stale-threshold-days is classified as DEAD.

The label limits apicurio.limits.config.max-artifact-labels and apicurio.limits.config.max-label-size.bytes are now enforced. In earlier versions, they could be set but had no effect. Both are off by default. If your configuration sets them, requests that create artifacts or versions, or update their metadata, with more labels or larger labels than these limits allow, now fail with HTTP 409. For a label, the size is the number of UTF-8 bytes of its key and value together.

apicurio.limits.config.max-property-key-size.bytes and apicurio.limits.config.max-property-value-size.bytes, which separately bound a label’s key and value, now count UTF-8 bytes instead of characters. A non-ASCII key or value that fit under the character count can now exceed the byte limit and start failing with HTTP 409.

quarkus.http.enable-compression now defaults to false. This setting never compressed REST responses, which Apicurio Registry compresses separately through apicurio.rest.compression.enabled; nothing that was compressed before 3.4 stops being compressed.

Changes for client applications in Apicurio Registry 3.4

The core REST API in Apicurio Registry 3.4 only adds endpoints, fields, and enum values, with the following changes to existing behavior.

Replacing the versions of a branch

PUT /groups/{groupId}/artifacts/{artifactId}/branches/{branchId}/versions returns HTTP 404 when a listed version does not exist, and HTTP 409 when the same version is listed more than once. Before 3.4, both requests failed with HTTP 500.

Protobuf message indexes

The Protobuf serializer writes the message index of the first message type in a schema as the single byte 0x00, as Confluent serializers do. Before 3.4, it wrote two bytes, 0x02 0x00. Deserializers of Apicurio Registry 3.1 and later read both forms, so producers and consumers can be upgraded in any order.

Auto-registration of identical schemas on multiple topics

When one serializer writes the same schema content to more than one topic, for example with TopicIdStrategy, Apicurio Registry now auto-registers a separate artifact for each topic, instead of caching the first topic’s registration and reusing it for the others. Each topic’s compatibility and validity rules now run, and messages for a topic carry that topic’s own artifact ID rather than the first topic’s. Consumers are not affected, because the schema content is identical.

Invalid rule configuration is now rejected at write time

Creating or updating a global, group or artifact rule now validates the configuration against the levels the rule type supports, and returns HTTP 400 if it is not one of them. Before 3.4, an invalid configuration was stored, and every later write to the artifact failed with HTTP 500 instead.

Compatibility groups are enforced

A new version now records the artifact’s compatibility group in its labels, and the compatibility rule compares it only with versions of the same group. Before 3.4, the compatibility group was accepted but ignored, and every version was compared regardless of group. Artifacts with no group are unaffected.

Concurrent promotions and status changes now conflict instead of racing

Promoting a contract, changing its status, and the metadata update that can accompany either are now compare-and-set: if the stage or status changed since the request was validated, it fails with HTTP 409 instead of applying on top of a stale read.

Artifact type webhook failures

A webhook failure during validation now rejects the request instead of silently accepting the content. A webhook failure during compatibility checking, canonicalization, dereferencing, or reference finding now fails with HTTP 502 and a generic message, instead of silently falling back to a less precise result or leaking exception text. Webhook calls now have a connect timeout (apicurio.artifact-types.webhooks.connect-timeout.seconds, default 5) and a read timeout (apicurio.artifact-types.webhooks.read-timeout.seconds, default 10), so an unreachable webhook now fails after about 10 seconds instead of about 25 seconds per call.

A malformed Basic authentication header now returns 401

A Basic authentication header that is not valid Base64 is now treated as missing credentials, and the request fails with HTTP 401. Before 3.4, it failed with HTTP 500 and exception text in the response.

Disabled versions through the v2 API

GET /apis/registry/v2/ids/globalIds/{id} for a version in state DISABLED now returns HTTP 404, matching the v3 API. Before 3.4, the v2 API returned the content of a disabled version.

New GOVERNANCE rule type

RuleType gets a new value, GOVERNANCE, for a rule that checks contract.* labels on data contract artifacts. A client built against an earlier version’s enum, including older SDKs and the v2 API, sees an unknown value if a GOVERNANCE rule is configured on a registry it talks to.

Changes for custom artifact types in Apicurio Registry 3.4

Apicurio Registry 3.4 can detect the type of an artifact from the extension of its content file, for example in GitOps storage. Custom artifact types configured in artifact-types.json can declare their own extensions with the new optional fileExtensions property. If two artifact types declare the same extension, Apicurio Registry does not start.

If you build Apicurio Registry with your own Java implementation of the artifact type provider interfaces, from schema-util/util-provider, note the following changes:

  • io.apicurio.registry.types.provider.ArtifactTypeUtilProviderFactory has a new method, Map<String, String> getFileExtensionToTypeMap(). It is abstract, so an implementation of the interface must add it. Alternatively, extend DefaultArtifactTypeUtilProviderImpl, which implements it.

  • DefaultArtifactTypeUtilProviderImpl builds the map in validateFileExtensions(), which also rejects an extension that two providers declare. The constructor DefaultArtifactTypeUtilProviderImpl(true) calls it after it loads the standard providers. A subclass that loads its providers itself, or uses the constructor without arguments, must call validateFileExtensions() after loading them, or the map stays empty.

  • io.apicurio.registry.types.provider.ArtifactTypeUtilProvider has a new method, Set<String> getFileExtensions(). It has a default implementation that returns no extensions, so existing providers keep working.

Custom artifact types that use webhooks, or Java classes named in artifact-types.json, are not affected.

Changes to experimental features in Apicurio Registry 3.4

Experimental features can change between minor versions. The following change affects deployments that enabled one in an earlier version.

ARD agents endpoint

With apicurio.ard.enabled=true, GET /.well-known/ard/agents returns a paginated response with items, total, and pageToken, as the ARD Registry API expects. In 3.3, it returned the AI Catalog format, with the next page in nextPageToken.

Setting an experimental feature through the dynamic configuration API

PUT /admin/config/properties/{propertyName} now returns HTTP 409, and leaves the stored value unchanged, when it would set an experimental feature’s dynamic property to true while apicurio.features.experimental.enabled is false. Before 3.4, the request succeeded, and GET /system/uiConfig reported the stored value even with the gate off, so the UI showed the feature as enabled. From 3.4, a value stored this way before the upgrade is also ignored while the gate is off: a deployment that turned a feature on through this API, without setting the gate, stops showing it after the upgrade. Set apicurio.features.experimental.enabled=true to keep it enabled. Today the only property this affects is apicurio.ui.features.agents.enabled, which controls whether the UI shows the Agents tab.
