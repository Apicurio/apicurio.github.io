Configuring Apicurio Registry with GitOps storage

Configure Apicurio Registry to use a Git repository as the source of registry data. With GitOps storage, you manage schemas and API designs declaratively in Git, and all changes flow through Git commits instead of REST API calls.

Prerequisites

  • You have a way to run the Apicurio Registry container image, for example Docker, Podman, or a Kubernetes cluster.

  • You have a Git repository for registry data.

Overview of GitOps storage

GitOps storage is a read-only storage variant that loads registry data from a Git repository. You declare the desired state of the registry in files, and the registry serves that state, so all changes flow through your Git workflow with reviews, history, and rollbacks.

GitOps storage is an experimental feature. You must enable the experimental features gate (APICURIO_FEATURES_EXPERIMENTAL_ENABLED=true) to use it. The data format (*-v0) might change in future releases.

Architecture

GitOps storage uses a polling-based architecture with blue-green database switching:

  1. The registry reads a local Git clone on a mounted volume. The registry never fetches from remote repositories itself; a sync container or an external process updates the clone.

  2. The registry periodically checks the current commit of the clone. A debounce mechanism absorbs rapid sequences of pushes before a load starts.

  3. When the commit changes, the registry loads all data into an inactive in-memory database and validates it.

  4. After a successful load, the active and inactive databases switch atomically. If the load fails, the registry keeps serving the last successfully loaded data.

Data flows in one direction only: from Git to the registry. REST API calls that would modify data are rejected with an HTTP 409 response. The Apicurio Registry web console detects the read-only storage, switches to read-only mode, and shows a banner that tells users to update the source Git repository. The registry requires no external database, because data is loaded into in-memory storage from Git.

Relationship of repositories and registry instances

One repository can serve multiple registry instances, and one registry instance can aggregate multiple repositories. Each metadata file can declare which registry instances load it, and the registry loads only the data that references its own identifier.

When to use GitOps storage

GitOps storage is a good fit when:

  • You want schema and API changes to go through pull requests, reviews, and CI checks

  • You need a read-only registry where all changes flow through a Git workflow

  • You want to avoid operating an external database

  • You already manage configuration as code and want registry content to follow the same model

GitOps repository data format

A GitOps repository contains metadata files that describe registry content, and plain schema files that hold the content itself. This section describes the file types, their discovery, and their fields.

No fixed directory structure is required. The registry discovers metadata files anywhere in the repository by file name suffix. By default, files ending in .registry or .ar, combined with the .yaml, .yml, or .json extensions, are treated as metadata files, for example order-event.registry.yaml. You can change the suffixes with the apicurio.polling-storage.file-suffixes property.

Each metadata file declares its kind with a $type discriminator:

Table 1. Metadata file types
Type Purpose and main fields

registry-v0

Registry configuration. Fields: registryId, globalRules (list of ruleType and config pairs), properties, and peers (list of peer registries; see below). The registryId value must match the apicurio.polling-storage.id property of the registry instance.

group-v0

An artifact group. Fields: registryIds (list), groupId, description, labels, owner, artifactsType, rules, createdOn, and modifiedOn. Every group that an artifact references must be declared by a group-v0 file; the registry does not create groups automatically.

artifact-v0

An artifact with its versions declared inline. Fields: registryIds, groupId, artifactId, artifactType (optional), name, description, labels, owner, createdOn, modifiedOn, rules, validatedUpTo, and versions. Each version has version, state, and content, where content is a relative path to a schema file. A version can also have name, description, labels, owner, globalId, createdOn, modifiedOn, and contentMetadata, which is a relative path to a content-v0 file.

content-v0

Optional content metadata, for explicit content identifiers and references. Fields: contentId, content (relative path to the schema file), and references (list of entries with groupId, artifactId, version, and name).

GitOps storage and KubernetesOps storage share one data format. The KubernetesOps field reference lists the type and description of each field except createdOn, modifiedOn, and validatedUpTo. The rules later in this section describe those three fields.

The following example declares a registry configuration, a group, and an artifact. All three files are required: a load that references an undeclared group fails, and the registry does not become ready.

$type: registry-v0
registryId: main
globalRules:
  - ruleType: VALIDITY
    config: FULL
$type: group-v0
groupId: my-schemas
$type: artifact-v0
groupId: my-schemas
artifactId: order-event
artifactType: AVRO
versions:
  - version: "1.0.0"
    state: ENABLED
    content: order-event-1.0.0.avsc

Content files are plain schema files that metadata files reference by a path relative to the directory of the metadata file.

When artifactType is omitted, the registry determines the type in the following order:

  1. Unambiguous file extension: extensions listed in the table below are mapped directly to a single artifact type. An explicit artifactType always takes precedence over the extension. A mapped extension is treated like a declared artifactType: the content is not checked against it, so an OpenAPI document saved as api.avsc is stored as AVRO unless a validity rule rejects it.

  2. Content-based detection: for ambiguous extensions (.json, .yaml, .yml, .xml) where multiple artifact types are possible, the registry inspects the file content to determine the type.

  3. Error: if neither the extension nor the content identifies a type, the load fails with an error listing the supported extensions.

All versions of an artifact must share the same type. When artifactType is omitted and versions resolve to different types from their extensions, the load fails with an error asking you to set artifactType explicitly.

The following additional rules apply:

  • If registryIds is omitted or empty on a group or artifact, any registry instance loads it.

  • The createdOn and modifiedOn timestamps on groups, artifacts, and versions are optional. When omitted, the registry uses the Git commit time. Supported formats are ISO 8601, with or without a time zone or as a date only, and Unix milliseconds.

  • The optional validatedUpTo field on an artifact controls rule validation during a load. When unset, only the latest version is validated, against all preceding versions. When set to a version identifier, versions up to and including that version are not re-validated. When the value matches no version, all versions are validated.

  • A group with no artifacts is loaded with its metadata and rules. This is useful for reserving a group namespace or applying group-level rules before any artifacts are added.

  • An artifact with no versions is loaded with its metadata and rules, but artifactType must be set explicitly. Without it, the load fails with an error because the type cannot be inferred from content. In previous versions, versionless artifacts were silently skipped.

  • The optional peers list on the registry configuration declares peer registries. Each entry has peerId (lowercase letters, digits, ., _, and - only; must be unique and cannot be local, which is reserved), url, optional name and description, enabled (defaults to true when omitted), and an optional credentialSecretRef, which is a reference to a credential and never a secret value itself. The full peers list is replaced on every load: omitting the key, or setting it to an empty list, removes all previously loaded peers.

Configuring GitOps storage with a single repository

You can configure Apicurio Registry to load its data from a single Git repository that is available as a local clone on a mounted volume.

Prerequisites

  • You have a Git repository that contains a registry configuration file (registry-v0) and registry content.

  • You have a local clone of the repository, or a sync container that maintains one.

Procedure

  1. In your repository, verify that a registry configuration file exists and that its registryId value matches the registry instance identifier that you configure in the next step. The default identifier is main.

  2. Configure the registry with the following environment variables:

    APICURIO_STORAGE_KIND=gitops
APICURIO_FEATURES_EXPERIMENTAL_ENABLED=true
APICURIO_POLLING_STORAGE_ID=main

  3. Mount the local clone of the repository into the registry container at /repos/default. A read-only mount is sufficient for serving content, because the registry does not write to the repository. If you use dry-run validation, mount the workspace writable instead, because the registry writes validation request files under the workspace directory. The mount path is the workspace directory (apicurio.gitops.workspace, default /repos) combined with the repository directory name (apicurio.gitops.repo.dir, default default).

    For example, with Docker Compose:

    volumes:
  - ./example-repo:/repos/default:ro

  4. Optional: To read from a branch other than main, set the APICURIO_GITOPS_REPO_BRANCH environment variable. If the configured branch does not exist in the clone, the registry falls back to HEAD.

  5. Start the registry.

  6. Verify the synchronization status:

    $ curl http://localhost:8080/apis/registry/v3/admin/gitops/status

    The registry reports not ready on its readiness probe until the first load succeeds. After the first successful load, it stays ready even if a later load fails, and it keeps serving the last successfully loaded data. With the default poll and debounce settings, expect a new commit to become visible after roughly 20 to 30 seconds.

Configuring the GitOps sync container

The registry reads only local Git clones and never contacts remote repositories. You can run the GitOps sync container next to the registry to keep a local clone up to date with a remote repository, or to accept pushes directly.

Prerequisites

  • You have configured the registry for GitOps storage.

  • For pull mode, you have the URL of a remote Git repository.

Procedure

  1. Run the quay.io/apicurio/apicurio-registry-gitops-sync container so that it shares a volume with the registry. Mount the shared volume at /repos in both containers, read-only in the registry container.

  2. For pull mode, which is the default, set the remote repository URL:

    APICURIO_GITOPS_REPO_URL=https://github.com/my-org/my-registry-data.git

    The sync container clones the repository and then updates it every 30 seconds. You can change the interval with the APICURIO_GITOPS_PULL_INTERVAL environment variable.

    For a private repository, use an SSH URL and provide the keys as described in the next step. The sync container has no setting for HTTPS credentials. A private HTTPS repository requires credentials in the URL itself, for example https://<token>@github.com/my-org/my-registry-data.git. Git saves that URL, including the credentials, in the configuration of the clone on the shared volume, which the registry container also mounts.

    With the Apicurio Registry Operator, you set the URL in the ApicurioRegistry3 custom resource, and the Operator copies it unchanged into the Deployment as an environment variable of the sync container. Anyone who can read the custom resource, the Deployment, or the pod can read the token. The sync container clones a repository only if the clone does not exist, and it fetches updates from the URL that Git saved in the clone. A changed token therefore takes effect only when the sync container creates the clone again. The Operator uses an emptyDir volume by default, so each new pod starts without a clone. If you use a persistent volume instead, delete the clone before you restart the sync container.

  3. Optional: For SSH remotes, provide the private key and the known hosts file:

    APICURIO_GITOPS_PULL_SSH_KEYS=/etc/gitops/ssh/id_ed25519
APICURIO_GITOPS_PULL_SSH_KNOWN_HOSTS=/etc/gitops/ssh/known_hosts

  4. Optional: Adjust the security level with the APICURIO_GITOPS_SECURITY environment variable. The default level, strict, rejects loose key file permissions, and fails at startup when an SSH remote is configured without any SSH keys. When you provide keys without a known hosts file, the container accepts a host key on first connection. The dev level relaxes host key checking for development. Plaintext http:// remote URLs are rejected at both levels.

  5. Optional: To accept Git pushes instead of pulling from a remote, set APICURIO_GITOPS_MODE=push. The sync container runs a restricted SSH server for the git user on port 2222. Configure the authorized client keys and the host key:

    APICURIO_GITOPS_PUSH_SSH_AUTHORIZED_KEYS=/etc/gitops/ssh/authorized_keys
APICURIO_GITOPS_PUSH_SSH_HOST_KEY=/etc/gitops/ssh/host_key

    Clients then push to the container directly:

    $ git push ssh://git@registry-host:2222/repos/default

    In push mode, any authorized push user can access all Git repositories on the shared volume.

  6. Optional: When you configure multiple repositories, set the mode per repository with APICURIO_GITOPS_REPOS_N_MODE, which overrides the global APICURIO_GITOPS_MODE setting.

Configuring multiple GitOps repositories

You can configure one registry instance to aggregate data from multiple Git repositories, for example one repository per team. The registry detects conflicting artifact definitions across repositories and rejects them.

Prerequisites

  • You have configured the registry for GitOps storage.

Procedure

  1. Configure the repositories on the registry with indexed environment variables. Indexes must start at 0 and be consecutive:

    APICURIO_GITOPS_REPOS_0_DIR=platform
APICURIO_GITOPS_REPOS_1_DIR=fulfillment
APICURIO_GITOPS_REPOS_1_BRANCH=fulfillment

    Optional: Assign an identifier for status reporting with APICURIO_GITOPS_REPOS_N_ID. The default identifier is the directory name.

    Do not combine the single-repository variables (APICURIO_GITOPS_REPO_DIR, APICURIO_GITOPS_REPO_BRANCH) with indexed variables. The registry rejects mixed configuration, index gaps, duplicate repository identifiers, and duplicate directory and branch combinations at startup.

  2. If you use the sync container, configure the remote URL for each repository with APICURIO_GITOPS_REPOS_N_URL, and optionally per-repository SSH keys with APICURIO_GITOPS_REPOS_N_SSH_KEYS.

  3. Ensure that each artifact is defined in exactly one repository. If the same groupId and artifactId combination is defined in more than one repository, the registry reports all conflicts and rejects the entire load.

  4. Verify the aggregated state:

    $ curl http://localhost:8080/apis/registry/v3/admin/gitops/status

    The sources field maps each repository identifier to the currently loaded commit.

    By default, the registry labels each loaded group and artifact with the identifier of its source repository, using the system:source label key. You can change or disable this with the apicurio.polling-storage.source-label-key property.

Validating repository changes before merging

You can validate a Git reference, such as a pull request branch, against the full registry validation pipeline without affecting the data that the registry serves. This enables CI checks that reject invalid schema changes before they merge.

Prerequisites

  • Validation is enabled on the registry (apicurio.gitops.validate.enabled, default true). When validation is disabled, the validation endpoints return an HTTP 503 response.

  • The sync container is running, because it fetches the reference to validate.

  • The workspace volume is writable by the registry, because the registry writes validation request files under the workspace directory.

Procedure

  1. Create a validation task for the reference:

    $ curl -X POST -H "Content-Type: application/json" \
  -d '{"type": "pull", "repoId": "platform", "ref": "refs/pull/42/head"}' \
  http://localhost:8080/apis/registry/v3/admin/gitops/validate

    The repoId value must be the identifier of a configured repository. The registry rejects a missing or unconfigured value with an HTTP 400 response that lists the configured identifiers. The value must also match the repository directory name, because the sync container resolves repoId by directory name. The registry accepts an identifier that you assign with APICURIO_GITOPS_REPOS_N_ID, but the created task then fails with an Unknown repoId error. The response contains a taskId.

  2. Poll the task until it completes:

    $ curl http://localhost:8080/apis/registry/v3/admin/gitops/validate/TASK_ID

    The task moves through the states pending, submitted, fetching, and validating to completed or failed.

  3. Check the outcome of a completed task in the result field, which is success or failure. A successful task reports group, artifact, and version counts. A failed validation reports structured errors with a detail message and, where available, the source repository and the context file path.

  4. Optional: Delete a task that you no longer need:

    $ curl -X DELETE http://localhost:8080/apis/registry/v3/admin/gitops/validate/TASK_ID

    Tasks are removed automatically after a time to live, which is one hour by default. To limit disk usage, at most five tasks hold disk resources at the same time by default; further requests are queued.

GitOps storage sizing considerations

With GitOps storage, each registry instance holds all of its data in memory and reloads all of it when a repository changes. Memory use and load time therefore grow with the total amount of data in your repositories, not with the size of a commit.

Each registry instance has two in-memory databases. The active database serves requests, and the inactive database receives the next load. The registry clears the inactive database only when the next load or dry-run validation starts, so both databases can hold a full copy of the data at the same time. Plan memory for at least two copies of the registry data. While a load runs, the registry also holds in memory the files that it reads from the repositories.

A load reads all of the data from every configured repository, not only the files that changed. Because the registry is not ready until the first load succeeds, startup time also grows with the amount of data.

The shared volume holds one clone of each repository. In pull mode, the clone is shallow by default and contains only the configured branch. In push mode, the repository on the volume keeps the full history that clients push to it, so the volume grows with that history. While a dry-run validation task runs, the volume also holds a shallow clone of the reference that the task validates.

GitOps storage limitations and troubleshooting

GitOps storage is read-only and produces no change events. This section lists these limitations and the checks to make when a registry instance does not become ready or does not show a commit.

GitOps storage has the following limitations:

  • The storage is read-only. REST API calls that modify data return an HTTP 409 response.

  • The registry produces no change events for the data that it loads from Git.

To find the cause of a problem, get the synchronization status from the /admin/gitops/status endpoint and read the syncState, errors, and sources fields. The acr gitops status command shows the same values in the Sync State, Errors, and Sources rows. The registry logs gitops update published after each successful load. After a load that it rejects, the registry logs gitops update failed to load, followed by the errors.

Table 3. GitOps storage problems and their causes
Problem Cause and resolution

The registry does not become ready.

The registry is ready only after the first successful load. If syncState is INITIALIZING and errors is empty, the registry has not yet read a commit from every configured repository. Check that the clone of each repository exists at the path that the registry reads and that the sync container, if you use one, is running. The registry logs GitOps repository directory does not exist while the directory is missing. If syncState is ERROR, the errors field lists what failed.

A load fails with the error Data source does not contain a registry configuration matching ID.

The registry found no registry configuration file with a registryId value that matches the apicurio.polling-storage.id property of the registry instance. The registry rejects such a load when the apicurio.polling-storage.require-registry-config property is true, which is the default. Add a registry configuration file with a matching registryId value, or set the apicurio.polling-storage.id property to the registryId value of an existing file. If a file with a matching registryId value exists, check its file name suffix and its $type value. The registry reads a file as a registry configuration only if the file has a metadata file suffix and the registry configuration $type value.

A commit does not appear in the registry.

Compare the sources field with the latest commit in the remote repository. If syncState stays IDLE and sources keeps showing an earlier commit, the new commit has not reached the local clone. The sync container logs Fetch failed when it cannot update the clone. If syncState is ERROR, a load or a poll failed, and the registry serves the last successfully loaded data. The registry does not load a commit again after a data error, so push a new commit that fixes the errors that the errors field lists.

Multi-replica deployments

This section describes how GitOps storage behaves in a multi-replica deployment: the per-replica volume model, synchronization modes, the convergence window, validation tasks across replicas, and sticky routing configuration.

Deployment model

In a Kubernetes deployment, a replica is one copy of the registry pod. A Deployment with replicas: 3 runs three identical pods, and a Service spreads incoming requests across them. When you run GitOps storage with multiple replicas, each replica operates independently with its own volume and its own sync sidecar.

Architecture

Each replica has:

  • Its own emptyDir volume, created empty when the pod starts and deleted with the pod.

  • Its own sync sidecar (apicurio-registry-gitops-sync), which clones the configured repositories into that volume.

No replica reads another replica’s volume. Every sidecar independently clones and fetches the same remote repositories, so all replicas converge on the same data. For a few seconds after a change, different replicas can serve different commits. This is the convergence window, described below.

In pull mode, this design avoids any single point of failure: if one pod is lost, its replacement clones the repositories again from the remote. No ReadWriteMany storage or cross-pod coordination is required. In push mode, an emptyDir volume is deleted with the pod, and the sidecar has no remote to clone from, so a pod replacement starts with an empty repository. See Synchronization modes and replicas for details.

Volume strategy

GitOps storage uses an emptyDir volume per pod. This is the default and the only volume type that the Apicurio Registry Operator configures.

emptyDir

Each pod gets its own volume that is created empty on startup and deleted with the pod. Nothing outside the pod can see it. The Apicurio Registry Operator configures this automatically.

A PersistentVolumeClaim (PVC) with ReadWriteOnce access mode is not suitable for multi-replica Deployments:

  • Pods on different nodes: A ReadWriteOnce PVC can only be mounted by pods on a single node. When Kubernetes schedules a replica onto a different node, the pod remains in ContainerCreating with a Multi-Attach error because the volume is already attached to another node.

  • Pods on the same node: Kubernetes can mount the volume into multiple pods on the same node, but the sidecars all write to the same directory. This causes conflicts and is not supported.

A PVC must never be shared by more than one pod. A PVC per pod would require a StatefulSet with volumeClaimTemplates, but the Apicurio Registry Operator uses a Deployment. A shared volume accessible to all replicas is planned (#10610).

Synchronization modes and replicas

The synchronization mode determines whether multiple replicas can run.

Pull mode (recommended for high availability)

Every sidecar pulls from the same remote repository independently. Any replica can serve requests, and losing one does not lose data because the replacement clones the repository again from the remote. Pull mode is the default.

Push mode (single replica only)

In push mode, CI runs git push to an SSH server in the sidecar, reached through a Service. A Service sends each connection to one of its pods, so the push lands in one pod’s volume and the other replicas never receive it. Their data silently diverges. For this reason, push mode supports a single replica only.

Because push mode uses an emptyDir volume and the sidecar has no remote repository to clone from, a pod replacement (by a rollout, node drain, or eviction) starts with an empty repository. The registry has no data until CI pushes again, and with a single replica nothing serves in the meantime. To mitigate this, CI should push on a schedule as well as on change. Operator support for a persistent volume in this case is tracked in #11132.

An emptyDir survives container restarts within the same pod. Only a full pod replacement deletes the volume.
Do not configure replicas > 1 with push mode. Running push mode with multiple replicas causes silent data divergence across replicas. In push mode, the Apicurio Registry Operator always runs one replica with the Recreate deployment strategy, and creates no HorizontalPodAutoscaler or PodDisruptionBudget. Recreate matters even with a single replica: every rollout has a short outage while the old pod terminates and the new one starts. If replicas > 1 or autoscaling is set, the Apicurio Registry Operator also records a ValidationError condition on the CR explaining that the setting is ignored.

Convergence window

In pull mode, each sidecar fetches updates from the remote independently. After a new commit is pushed to the remote, each sidecar picks it up on its next pull cycle. Until all sidecars have fetched the new commit and their registries have loaded it, different replicas can serve data from different commits.

This period is the convergence window. With the default pull interval of 30 seconds and the default poll and debounce settings, convergence typically takes around 60 seconds under healthy, lightly loaded conditions: the sidecar that pulls last is at most one pull interval behind, and the registry needs an additional poll-plus-debounce cycle to load the new data. Under load or with slow Git fetches, convergence can take longer.

Detecting the convergence window

Use the GitOps status endpoint to check which commit each repository is serving:

$ curl http://localhost:8080/apis/registry/v3/admin/gitops/status

The sources field in the response maps each repository identifier to the abbreviated commit that the replica has loaded. When you query different replicas (for example, by targeting individual pod IPs), the commit values can differ during the convergence window.

To verify that all replicas have loaded a specific commit, compare the sources values against the expected target commit. Equal values alone do not confirm convergence: all replicas initially report the previous commit, and a failed load retains the old commit in the status. Also check the syncState field for errors. Only when every replica reports the expected commit with no errors has the convergence window closed.

Validation tasks across replicas

Dry-run validation is asynchronous. The client sends a POST request to create a task and receives a task ID, then polls a GET endpoint until the task finishes. The pod that receives the POST writes a request file to its volume, its sidecar fetches the reference, and that same pod runs the validation.

Self-describing task IDs and cross-replica polling

The task ID encodes the validation request itself (the repository ID, reference, and type), signed with an HMAC key. Any replica that receives a GET for an unknown task ID can decode it, start the same validation on its own volume, and return its own result. No replica needs anything from another.

For this to work across replicas, all replicas must share the same HMAC key via apicurio.gitops.validate.hmac-key. Without a shared key, each replica generates its own random key at startup, and a GET on another replica returns 404 instead of decoding the task ID. The key must be at least 32 bytes. Supply it from a Kubernetes Secret:

env:
  - name: APICURIO_GITOPS_VALIDATE_HMAC_KEY
    valueFrom:
      secretKeyRef:
        name: registry-gitops-hmac
        key: hmac-key

With the Apicurio Registry Operator, place the same env entry under spec.app.env in the ApicurioRegistry CR:

apiVersion: registry.apicur.io/v1
kind: ApicurioRegistry3
metadata:
  name: my-registry
spec:
  app:
    env:
      - name: APICURIO_GITOPS_VALIDATE_HMAC_KEY
        valueFrom:
          secretKeyRef:
            name: registry-gitops-hmac
            key: hmac-key

Operator-managed HMAC key distribution is tracked in #11189.

Grace period

When a replica receives a GET for an unknown task ID, it waits apicurio.gitops.validate.grace-period.seconds (5 seconds by default) before starting its own validation. This gives the creating replica time to finish first. Without sticky routing, or when repeated work is too frequent, increase the grace period. The cost is a later result if the creating replica is lost. Keep the grace period well below how long clients wait for a result, such as the CLI’s --timeout.

Duplicate requests

If a replica receives a POST for a validation that it already has pending or submitted, it returns the existing task instead of creating a duplicate.

This design has the following characteristics:

Repeated work

Without sticky routing, a client polling every few seconds can reach every replica, and each one runs the validation independently. Each replica limits how many validations it runs concurrently via the max-tasks setting (default 5). Use sticky routing (described below) to keep a client’s polls on the same pod and avoid repeated work. If sticky routing is not feasible, increase the grace period (described above) to reduce repeated work.

Listing

The GET /admin/gitops/validate (list) endpoint returns tasks from the replica that receives the request only. A task created on one replica is not listed on another.

Deleting

DELETE /admin/gitops/validate/{taskId} removes the task’s in-memory entry on the receiving replica, but only if the task is pending, completed, or failed. If the task is still in flight (submitted, fetching, or validating), the DELETE returns 409 Conflict. Wait for the task to finish or let it expire. Because the task ID is self-describing, a subsequent GET on any replica (including the one that deleted it) decodes the ID and starts the validation again. A task is fully gone only after it expires, controlled by apicurio.gitops.validate.task.ttl.seconds (3600 seconds by default).

Commit SHA vs. branch

CI should validate a full commit SHA (40 hexadecimal characters), not a branch name or abbreviated SHA. A branch can move while replicas are fetching it, and different replicas can end up validating different commits. An abbreviated SHA does not work because the sidecar’s fetch fallback requires the full SHA. The Git server must also allow fetching a commit by its SHA directly; GitHub and GitLab allow this by default, but other servers might not.

Example validation request with a commit SHA
$ curl -X POST -H "Content-Type: application/json" \
  -d '{"type": "pull", "repoId": "default", "ref": "a1b2c3d4e5f6a7b8c9d0e1f2a3b4c5d6e7f8a9b0"}' \
  http://localhost:8080/apis/registry/v3/admin/gitops/validate
Use sticky routing (described below) to keep a client’s polls on the same pod. This avoids repeated work and makes listing and deleting tasks consistent.

Configuring sticky routing

Sticky routing, or session affinity, keeps a load balancer sending the same client to the same pod. This is an optimization, not a correctness mechanism: without it, self-describing task IDs still produce the right answer, with some repeated work. You can configure sticky routing to reduce repeated validation work across replicas.

How to configure sticky routing depends on where the client’s requests enter the cluster.

Clients inside the cluster

Clients inside the cluster (for example, Tekton, Argo Workflows, or CI runners on the cluster) call the registry’s Service directly. Configure sessionAffinity: ClientIP on the Service:

apiVersion: v1
kind: Service
metadata:
  name: my-registry-service
spec:
  sessionAffinity: ClientIP
  sessionAffinityConfig:
    clientIP:
      timeoutSeconds: 3600

Kubernetes remembers which pod the client pod’s IP was sent to and keeps sending it there for up to the configured timeout (default 3 hours). The client pod’s IP does not change during a CI job, so this works well.

The Apicurio Registry Operator does not set sessionAffinity by default, because pinning clients to pods can unbalance load when a few clients produce most of the traffic. Enable it when you need it.

Operator-managed deployments

The Apicurio Registry Operator creates the registry Service and Ingress automatically. The CR cannot configure sessionAffinity on the Service or affinity annotations on the Ingress today (#11187). To use sticky routing with operator-managed deployments:

  1. Set spec.app.ingress.enabled: false in the ApicurioRegistry CR to disable the operator-managed Ingress.

  2. Create your own Service with sessionAffinity: ClientIP that selects the registry pods. Use the labels the operator sets, for example app.kubernetes.io/instance: <CR name> and app.kubernetes.io/component: app:

    apiVersion: v1
kind: Service
metadata:
  name: my-registry-affinity
spec:
  sessionAffinity: ClientIP
  sessionAffinityConfig:
    clientIP:
      timeoutSeconds: 3600
  selector:
    app.kubernetes.io/instance: my-registry
    app.kubernetes.io/component: app
  ports:
    - port: 8080
      targetPort: 8080

    The operator’s own Service still exists, so in-cluster clients must call your new Service by name to get affinity.

  3. Create your own Ingress or Route pointing at your Service, with the affinity annotations from the examples below.

The Apicurio Registry Operator does not manage these resources, so you must keep them in step with the CR manually, for example updating ports when TLS is enabled.

Clients outside the cluster through OpenShift Routes

OpenShift Routes use cookie-based affinity by default: the router sets a cookie on the first response and uses it to route subsequent requests to the same pod. For this to work, the client must send the cookie back.

Cookie-based affinity works only with HTTP, edge-terminated, and re-encrypt Routes. For TLS passthrough Routes, the router cannot read or set HTTP cookies inside the encrypted connection. Use source-IP-based affinity instead (haproxy.router.openshift.io/balance: source).

The apicurio-registry CLI keeps cookies within a command (#11155), so cookie-based affinity from the Route’s default configuration works for gitops validate polling. For TLS passthrough Routes (where cookie-based affinity does not work), configure source-IP-based affinity:

kind: Route
metadata:
  annotations:
    haproxy.router.openshift.io/balance: source

For other clients that support cookies, such as curl:

# Create the task and save cookies
$ curl -c cookies.txt -X POST -H "Content-Type: application/json" \
  -d '{"type": "pull", "repoId": "default", "ref": "refs/pull/42/head"}' \
  https://registry.example.com/apis/registry/v3/admin/gitops/validate

# Poll with the same cookies
$ curl -b cookies.txt \
  https://registry.example.com/apis/registry/v3/admin/gitops/validate/TASK_ID

Clients outside the cluster through nginx-ingress

For nginx-ingress, configure cookie-based or IP-based affinity with annotations on the Ingress resource:

# Cookie-based affinity
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  annotations:
    nginx.ingress.kubernetes.io/affinity: cookie
    nginx.ingress.kubernetes.io/session-cookie-name: REGISTRY_AFFINITY
    nginx.ingress.kubernetes.io/session-cookie-max-age: "3600"
# IP-based affinity (alternative)
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  annotations:
    nginx.ingress.kubernetes.io/upstream-hash-by: $remote_addr

Hosted CI runners

Hosted CI runners such as GitHub-hosted runners reach the internet through cloud NAT. Their outgoing IP can change during a job, so IP-based stickiness is best-effort for them. Cookie-based stickiness is more reliable if the CI tool supports it.
